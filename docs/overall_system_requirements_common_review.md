# 全体システム要件定義書（機能横断・共通編）レビュー指摘

**対象:** {doc}`overall_system_requirements_common`（第1.19版）
**位置づけ:** 文書修正リスト。1節から6節のすべてを第1.19版で反映済みである。

この文書は、共通編を Sphinx に載せた時点で見つかった修正点を残す。共通編は機能別文書の上位であり、画面・URL・作成 API・Cookie・課金判定が確定済みだと書いていたが、実際には機能別文書と複数箇所で食い違っていた。第1.19版で、残っていた1節・3節・4節・5節も文書側で閉じた。各節の見出しに反映先を書く。

> **第1.17版での扱い:** ホームの公開一覧・検索は廃止した。2.1節と4.1節の「公開一覧」に関する指摘は、一覧を別サービスへ分離したことで解消済みである。`visibility` は将来のメディアサイト用の予約列として残す。

## 1. 先に決めること（第1.19版で反映済み）

共通編 1.2 節に、正本の範囲を 2 つに分けて書いた。

1. この共通編が上書きする範囲（境界、公開フラグ、画面 ID、URL、アクターの動線、機能間の認可境界、課金の判定順、Cookie の名前と期限）。
2. 機能別文書に残す範囲（各画面の部品、API のフィールド、データベースの物理定義）。

どちらが勝つかを書く前は、正本が 2 つあった。

## 2. 文書の中で食い違っていた点（共通編 第1.1版で反映済み）

### 2.1. 公開一覧の URL

`SCR-PUB-00` のパスは `/` だけにした。`/events` は画面ではなく、`/events/[id]` のパス接頭辞である。ID のない `/events` は `/` へリダイレクトする。ジャーニー、IA、画面カタログ、遷移図、7.1 節をこれに揃えた。

### 2.2. 検索条件

カテゴリ検索は外した。イベントにカテゴリ項目はない。`PUBLIC` の検索は、キーワードと日付だけである。

### 2.3. 公開フラグとライフサイクル

共通編 2.3 節に組み合わせを書いた。

| 条件 | トップ `/` | 告知URL | 出欠 |
| :--- | :--- | :--- | :--- |
| `PUBLIC` かつ `PUBLISHED` かつ未削除 | 掲載する | 閲覧できる | 受け付ける |
| `UNLISTED` かつ `PUBLISHED` かつ未削除 | 出さない | 閲覧できる | 受け付ける |
| `CLOSED` かつ未削除 | 出さない | 閲覧できる | 停止する |
| `DRAFT`、または `isDeleted = true` | 出さない | 404 | 受け付けない |

完全削除は `isDeleted = true` の論理削除である。出欠受付停止は `status = CLOSED` である。公開後のホーム掲載（`PUBLIC`）と紹介制（`UNLISTED`）の切り替えは `SCR-ORG-05` で行う。新規作成の既定は紹介制である。

### 2.4. 会員登録

`SCR-PUB-02` はページ `/auth/register` だけにした。モーダル表記はカタログ、IA、7.1 節から外した。

### 2.5. 遷移図

公開完了から開く先は、ホーム公開・紹介制とも告知URL（`SCR-PUB-01`）にした。招待URLを発行した幹事は `SCR-ORG-07` へ進まない。受諾画面を開くのは、URLを受け取った別幹事である。

### 2.6. 排他ロック

期限切れのロックは通常取得で引き継ぎ、HTTP 409 にはしない。HTTP 409 と Takeover は、他の幹事が期限内のロックを持っているときだけである。Takeover はその期限内ロックを上書きする。

## 3. 既存仕様と衝突している点（第1.19版で反映済み）

### 3.1. イベント作成 API のパス

作成のパスが文書ごとに違う。

| 文書 | 作成のパス |
| :--- | :--- |
| 共通編 4.2 節、共通バックエンド実装仕様 | `POST /api/v1/public/events` |
| イベント紹介のシステム要件 | `POST /api/v1/organizer/events` |
| ユーザー管理の詳細設計 | `POST /api/v1/events` |

公開一覧を足すと、`/api/v1/public/events` は一覧取得の名前でもある。作成をこのパスに置くなら、その旨と、一覧 API の名前を共通編に書く。

### 3.2. 課金判定から支払い遅延が抜けている

4.2 節の優先順は次のとおりである。

1. 有効な月額サブスクリプションがあれば、枠を消費せず作成を許可する。
2. 単発クレジットが残っていれば、1 消費して許可する。
3. 無料枠の累計が 2 回未満なら、カウントを 1 増やして許可する。
4. どれもなければ HTTP 402 を返す。

ローカル手順と `src/lib/quota.ts` では、この前に `subscription_status` が `PAST_DUE` のとき作成できない。「有効」の定義（`ACTIVE` かつ期間内、など）も共通編にない。402 の前に支払い遅延を置き、「有効」の条件を書く。

### 3.3. ゲスト幹事と利用枠の主体がつながっていない

`SCR-ORG-02` は、認証済み幹事とゲスト幹事の両方が作成できる。課金ゲートは `canCreateEvent(userId)` で、利用枠の行は会員登録時に作られる。ゲストには `userId` がない。次の3つを、ゲストの筆頭作成者にどう適用するかが空いている。

* 無料 2 回。
* Stripe の単発購入と月額。
* 共同幹事は枠を消費しない、という免除。

公開要求の前に会員登録を必須にするか、ゲスト用の枠の持ち方を書くか、どちらかに決める。第1.11版の電話番号確認は、会員の捨てメールによる無料枠の複製を止める。ゲスト公開は利用枠を見ないままなので、この指摘は残る。

### 3.4. Cookie の期限と届く範囲

出欠トークンの期限と `Path` が文書ごとに違う。

| 文書 | 期限 | Path |
| :--- | :--- | :--- |
| 共通編 4.3 節 | 30 日 | 未記載 |
| イベント紹介のシステム要件 | 90 日 | `/events/{id}` |
| イベント紹介のバックエンド実装仕様 | 30 日（`Max-Age=2592000`） | `/` |

`Path` がイベント単位だと、`/auth/register` へその Cookie は送られない。4.3 節の「端末 Cookie 内の全トークンを 1 トランザクションで会員へ紐付ける」が成立しない。期限、`Path`、Hydration 時に集める Cookie 名を1つに揃える。

### 3.5. CRUD マトリクスが権限より広い

3.2 節のマトリクスは、操作の有無をアクターごとに置く表である。次の行は、既存の認可より広い。

* イベントの削除は、主催幹事全員が可になっている。API 仕様の削除はオーナーのみである。共同幹事との差がない。
* 参加者本人の一覧は不可になっている。マイページ（`SCR-PUB-03`）は、本人の申込一覧である。
* 利用枠は、主催者の作成・更新・削除がすべて可になっている。枠の行を作るのは会員登録と Stripe 側である。
* チラシ資産の削除が可になっている。他文書に、その操作の定義がない。

表の記号を、既存の認可に合わせるか、広げる理由を備考に書く。

### 3.6. 画面カタログから落ちている既存要素

5 節は画面カタログの完全版だと書いている。機能別文書にある次の要素が、共通編のカタログにない。

* `SCR-ORG-04` の公開 URL コピーと QR（イベント紹介のシステム要件）。
* `SCR-PUB-01` のカレンダー追加、地図、Sticky CTA（同）。
* 会員登録の Google サインイン、マイページのログアウト（フロントエンド実装仕様）。
* `/organizer/events/[id]`。ローカル手順では主催者向けのイベント詳細である。実装は編集画面へのリダイレクトである。

完全版にするなら、残すものと捨てるものを各画面の行に書く。

### 3.7. チラシを作る画面が動線にない

3.1 節の新規幹事は「告知ページとチラシを作りたい」で入り、着地はイベント作成（`SCR-ORG-02`）である。カタログにあるチラシ UI は、生成済み資産を選ぶ `SCR-ORG-03` だけである。新規生成の入口が IA にない。作成画面の中で生成するならその旨を書き、別画面なら画面 ID とパスを足す。

### 3.8. 複製と下書きが動線にない

データベース上、複製は `DRAFT` で作られる。共通編の作成は、公開要求の HTTP 201 一本である。複製が枠を消費するタイミングと、下書きを公開する操作が書かれていない。ジャーニーにある「過去イベントの複製」から、枠の消費時点まで線を引く。

## 4. 網羅のために足りない境界（第1.19版で反映済み）

### 4.1. 公開一覧の API がない

`SCR-PUB-00` を新設しているが、対応する取得 API がない。次を書く。

* メソッドとパス。
* 件数、ページ、並び。
* 日付条件の意味（開催日が指定日以降、など）。
* `UNLISTED`、下書き、終了、削除済みを一覧から外す条件。

### 4.2. 紹介制の制御が URL の秘匿だけになっている

2.2 節の `UNLISTED` は、一覧と検索に出さず、`/events/[id]` を直接開いた人だけが閲覧・出欠できる。次が未定義である。

* 検索エンジンへの掲載を禁止するか。
* 一覧 API が `UNLISTED` を返さないこと。
* 終了後、削除後の URL を 404 にするか、告知だけ残すか。

### 4.3. Prisma の共通モジュールのパスが違う

7.2 節は、単一インスタンスの置き場を `src/lib/db.ts` と書く。リポジトリの共通モジュールは `src/lib/prisma.ts` である。要件にファイル名を残すなら、実在するパスに直す。

## 5. 体裁（第1.19版で反映済み）

HTML 化したときに、次が本文のまま出る。

* `[cite: 1]` のような表記は、参照先がなく、角括弧の文字として残る。参照を残すなら、対象の Sphinx 文書へのリンクにする。
* 1.1 節の強調 `**「機能横断・共通要件定義書」**` は、かぎ括弧に挟まれた `**` が強調にならず、アスタリスクが文字として出る。かぎ括弧を強調の外に出す。
* 3.1 節の表にある `$\rightarrow$` は、数式拡張を使っていないため矢印にならない。ドル記号が残る。矢印の文字にする。
* 7.3 節の JSON 例は、`type` の値が URI ではなく、Markdown のリンク記法になっている。RFC 7807 の `type` は URI とする。

## 6. 第3節の画面の穴（共通編 第1.2版と実装に反映済み）

第3節の操作に置き場が無かったものは、共通編 3.4 節に書き、アプリへ入れた。

* サービス紹介の短い文は `/` の冒頭である。料金の比較は `/service`（SCR-PUB-06）に置く。
* チラシ生成は作成画面と編集画面のパネル（SCR-ORG-08）である。過去チラシの選択と削除は SCR-ORG-03 である。
* 複製の着地は編集画面（SCR-ORG-05）である。
* 削除と受付停止は筆頭幹事の SCR-MOD-03 である。
* 名簿は CSV、出欠の変更、参加者の削除、参加者へのリマインドを持つ。リマインドは会員へメール送信し、アカウントのない参加者には同じ文面をコピーして個別に送れる。
* Stripe Portal は主催一覧とマイページから開く。
* 公開一覧はキーワードと開催日で絞る。対象は `PUBLIC` かつ `PUBLISHED` かつ未削除である。

## 7. 第1.19版でどう閉じたか

第1.19版では、1節・3節・4節・5節も閉じた。実装を変えず、文書側で決めたものは次のとおりである。

* **3.1:** イベント作成は `POST /api/v1/public/events` の 1 本に統一した。`POST /api/v1/organizer/events` と `POST /api/v1/events` を書いていた機能別文書（イベント紹介のシステム要件、ユーザー管理の詳細設計とバックエンド実装仕様）を直した。
* **3.2:** 課金の判定順の先頭に `PAST_DUE` を置いた。「有効」は `subscription_status = ACTIVE` かつ `current_period_end` が現在時刻より後、と定義した。
* **3.3:** ゲストは利用枠を消費せず、端末の `org_token_*` で作れるのは 1 件までとした。2 件目は 403 `REGISTER_REQUIRED`。ゲスト専用の利用枠は作らない。
* **3.4:** `rsvp_token_<イベントID>`、`Max-Age` 30 日、`Path=/` に確定した。`Path` をイベント単位にすると、`/auth/register` と `/participant` でトークンを読めず Hydration が成立しないためである。
* **3.5:** 利用枠の行は画面から作らない。画面が行うのは購入と残数の参照だけにした。
* **3.6:** 画面カタログに地図リンクと Sticky CTA を足し、QR・カレンダー追加・SNS シェアは持たないと書いた。`/organizer/events/[id]` は置かず、ID だけの URL は 404 とした。
* **4.2:** 告知ページは `noindex, nofollow`、一覧 API は持たない、`CLOSED` は URL を残す、論理削除と下書きは 404、と決めた。
* **4.3:** `src/lib/db.ts` を `src/lib/prisma.ts` に直した。
* **5:** `[cite: n]` を外し、かぎ括弧の強調、`$\rightarrow$`、RFC 7807 の `type` を直した。

残っているのは、QR・カレンダー・SNS シェアの実装である。これは文書ではなく機能追加なので、必要になった時点で別の Issue にする。
