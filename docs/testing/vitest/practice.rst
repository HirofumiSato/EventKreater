何をすべきか
============

読む順の 7 番です。前は :doc:`run-cycle`、次は :doc:`../scope` です。

このページは、テストを 1 本足すときに何をするかと、落ちたときに何を直すかを決めます。

テストを足す 5 手順
-------------------

.. list-table::
   :header-rows: 1
   :widths: 8 26 66

   * - 順
     - すること
     - 注意
   * - 1
     - 対象を決める。関数 1 つ、Route Handler 1 つ、画面 1 つ
     - 「何を確かめたいか」が 1 文で言えないなら、まだ切れていない
   * - 2
     - 置き場所とファイル名を決める
     - ``tests/unit/対象.test.ts``。拡張子は ``.ts``。``.test.tsx`` は集められない
   * - 3
     - ``it`` の名前を日本語で書く
     - 「〜なら〜する」「〜を1ミリ秒でも過ぎたら〜」のように条件を書く。実装の関数名をなぞるだけにしない
   * - 4
     - 失敗する状態で 1 回走らせる。``npx vitest run tests/unit/対象.test.ts``
     - 最初から緑なら、そのテストは何も確かめていない
   * - 5
     - 実装を直して緑にし、``npm run check`` を通す
     - 型は ``tsc``、体裁は ESLint が見る。テストが緑でも ``check`` は落ちうる

赤から緑へ
----------

**期待値を実装に合わせて緩めません。** 落ちたときは、まずどちらが誤りかを決めます。

.. list-table::
   :header-rows: 1
   :widths: 30 34 36

   * - 落ち方
     - 原因
     - 直す場所
   * - 期待した例外が出ない
     - 実装の分岐が抜けている
     - 製品コード。``it`` の名前が仕様なら、仕様側が正
   * - 期待と違う値が返る
     - 境界の比較（``>`` と ``>=``）、優先順、丸め
     - 製品コード。仕様の数値を ``docs/`` で確認してから直す
   * - ``TypeError: xxx is not a function``
     - import 違い、モックの形が違う
     - テスト側
   * - ``document is not defined``
     - ``environment: "node"`` のまま画面のコードを触った
     - テスト側。jsdom を入れるか、対象を純粋関数に寄せる
   * - 件数が増えない
     - ``include`` に合っていない（``.test.tsx``、``tests/`` の外）
     - ファイル名か置き場所
   * - 全部 skip になる
     - ``TEST_DATABASE_URL`` が無い
     - 環境。テスト側ではない

判断の流れを 1 枚にすると次のとおりです。

.. mermaid::

   flowchart TD
       A["テストが落ちた"] --> B{"期待した例外や値と、実装のどちらが仕様か"}
       B -->|仕様はテスト側| C["製品コードを直す"]
       B -->|仕様は実装側| D["テストの期待値を直す。ただし理由を残す"]
       B -->|判断できない| E["docs の要件を読む"]
       E --> C
       A --> F{"エラーの種類"}
       F -->|TypeError か import 失敗| G["テスト側の配線を直す"]
       F -->|document is not defined| H["jsdom を入れるか対象を変える"]
       F -->|件数が 0| I["ファイル名と置き場所を確認する"]
       C --> J["npm run check"]
       D --> J
       G --> J
       H --> J
       I --> J
       J --> K{"緑か"}
       K -->|いいえ| A
       K -->|はい| L["コミットする"]

やってはいけない
----------------

* ``it.skip`` で逃げる。落ちているテストを skip すると緑になりますが、確かめていないだけです。直すか、要件から外すかを決めます。
* ``expect`` を緩める。``toBe(402)`` を ``toBeGreaterThanOrEqual(400)`` にすると、403 でも通ります。
* ``TEST_DATABASE_URL`` に開発用 DB を書く。``tests/setup/db.ts`` が ``DATABASE_URL`` を上書きするので、開発用の行がそのまま消えます。
* 時刻を実時刻のまま使う。「24 時間以内」のような境界は、引数で時刻を渡すか ``vi.useFakeTimers()`` で固定します。今の ``assertGuestEditWindow`` は引数で受け取る形です。
* 結合テストで後片付けをしない。``afterEach`` で消さないと、次の実行が前回の行を見ます。
* ``npm test`` だけで判断する。型と体裁は見ていません。``npm run check`` まで通します。

レビューで見る点
----------------

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 観点
     - 合格の形
   * - 名前
     - ``it`` の名前だけで条件が分かる。仕様の数値か HTTP ステータスが入っている
   * - 独立性
     - 単体で走らせても通る。実行順を変えても通る
   * - 時刻
     - 実時刻に依存していない
   * - 外部 I/O
     - Stripe、OpenAI、チラシ API へ出ていない。Prisma はテスト用 DB か偽物
   * - 後片付け
     - 作った行を消している
   * - 断言の強さ
     - ステータスだけでなく、``error`` のコードと ``type`` まで見ている
   * - 型
     - ``tsc --noEmit`` が通る。``as any`` で逃げていない
