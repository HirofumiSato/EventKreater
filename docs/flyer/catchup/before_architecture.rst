アーキテクチャの前に
====================

:doc:`/flyer/architecture` は、処理の中身より「どのファイルが何を知ってよいか」を説明します。図を読む前に、次の三点だけ押さえてください。

フォルダは役割で分かれている
----------------------------

``src/`` のフォルダは、機能の種類ではなく、変わる理由で分かれています。

* ``api/`` は、外から来る HTTP の形を知ります。
* ``usecases/`` は、1 回の生成の順番だけを知ります。
* ``ports/`` は、依頼の窓口（メソッド名と引数）だけを知ります。
* ``adapters/`` は、OpenAI や Pillow という具体的な道具を知ります。
* ``domain/`` は、タイトルや日付といったデータの形を知ります。
* ``infrastructure/`` は、設定ファイルとディスクへの保存を知ります。

上にあるものほど「何をしたいか」、下にあるものほど「どの製品でやるか」です。

図は上から下へ読む
------------------

アーキテクチャの図は、リクエストが届いてから部品へ渡る順です。

1. HTTP が JSON を受け取る。
2. ユースケースが順番を進める。
3. ユースケースはポート（窓口）だけを呼ぶ。
4. 起動時に差し込まれたアダプターが、その窓口の実作業をする。

「注入」は、クラスの中で ``OpenAI()`` と書かず、``main.py`` が選んだオブジェクトをコンストラクタへ渡すことです。キーが無ければモック、あれば OpenAI、と同じ窓口に別の実装を渡せます。

知ってよいことの境界
--------------------

ガイドは「レンダラーは HTTP クライアントを import しない」と書きます。これは、文字を描くファイルが通信ライブラリを参照しない、という意味です。

境界があると、文字の位置を直す変更が課金 API の呼び出しを巻き込みません。テストも、ネットへ繋がずに描画だけを実行できます。逆に、プロンプトエンジンは座標計算を import しません。文章の解釈と、ピクセルの配置は別の仕事です。

:doc:`architecture_words` でポート、アダプター、モックの定義を確認してから、ガイドの図に戻ってください。
