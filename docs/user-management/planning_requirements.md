# プロジェクト企画要件定義書
## イベント主催者・参加者向け 権限管理＆段階的会員基盤（Progressive Membership & Lean RBAC）

## 1. 目的と位置づけ（階層構造）

本ドキュメントは、システム要件定義および実装仕様の策定に先立ち、イベント管理プラットフォームにおける「参加の摩擦極小化」と「幹事ガバナンス・再利用性」を両立するための目的関数を定義するものである。

```text
【最上位：企画要件（本ドキュメント）】
  └ 誰のどんな痛みを、既存代替品と比べてどう解決し、どう事業成立させるか
      ├ 参加者：登録ゼロで参加完了 ＋ 蓄積価値による自然な会員化
      └ 幹事：セキュアな共同運営 ＋ 排他ロックによる事故防止 ＋ 過去資産の再利用
      ↓
【次工程：要件定義書（システム境界・機能/非機能）】
  └ ケイパビリティURL設計、リースロック排他制御、アカウント統合（Account Merging）の境界
      ↓
【最終工程：仕様書（APIスキーマ・トークン仕様・DBスキーマ）】
  └ セッションストレージ、JWTクレーム、楽観/悲観ロックAPIパラメータ、データマイグレーション定義
```

## 2. 企画要件コア5項目

### 2.1. ターゲットの解像度と現状の代替手段

#### ペルソナと行動コンテキスト
* **ペルソナA（幹事・主催者）:** 
  * 社内勉強会、コミュニティイベント、飲み会、サークル等の企画者（2〜4名の有志チームで運営）。
  * 共同で文面を修正したり参加者リストを確認したいが、特定個人のGoogleアカウントやパスワードを共有運用することに心理的・セキュリティ的抵抗がある。
* **ペルソナB（参加者）:** 
  * 幹事から送られてきたURLを開き、スマートフォンで移動中や休憩中に30秒以内で出欠のみを回答したいユーザー。
  * 「パスワード設定」「メール認証コード待ち」が発生した瞬間にブラウザを閉じる（フォーム離脱）。しかし、直前になって「何時集合だったか」「参加登録できているか」を確認したい。

#### 現状の代替手段（As-Is）と課題
* **調整さん / LINE日程調整:**
  * 手軽だが、URLを知っている全員に参加者氏名やコメントが全公開され、社内・プライベートの機微情報が漏洩する（プライバシー欠如）。
  * 誰でも他人の名前で書き換え・削除ができてしまう脆弱性がある。
* **Peatix / Connpass / Doorkeeper:**
  * 参加者全員にアカウント登録を強制するため、カジュアルな社内イベントやライトな集まりでは参加障壁（Friction）が極めて高い。
* **Googleフォーム / スプレッドシート:**
  * 共同管理はしやすいが、回答者が後から「自分の回答状態」を確認・修正する導線が複雑であり、幹事の個別問い合わせ対応負荷が増加する。

### 2.2. 独自の提供価値（Core Value Proposition）

#### 1. 段階的アイデンティティ（Progressive Identity / Zero-Friction RSVP）
* **登録ゼロで即時回答:** 参加者はアカウント作成不要。氏名（ニックネーム可）と出欠選択のみで即座に確定。
* **ステートレスな状態確認:** 回答完了時に発行されるセッショントークン／固有URLにより、未登録のままでも後から自身の登録状況の照会・修正が可能。
* **蓄積価値によるアカウント昇格（Account Hydration）:** 「会員登録すると、参加したイベントが一覧化される」というメリットを提示し、後から会員登録した時点で過去の参加ログを自動紐付けする。

#### 2. 軽量かつ堅牢な幹事ガバナンス（Lean Co-Organizing & Concurrency Safety）
* **厳格な権限分離（主催者秘匿性）:** 参加者一覧および個人情報は「幹事権限を持つユーザー」のみが閲覧可能（参加者への情報漏洩を物理遮断）。
* **非同期共同編集と排他ロック（Mutual Exclusion）:** 複数幹事によるURLベースの共同管理を許可しつつ、デッドロックや先祖返りを防ぐため「同時編集不可（排他的リースロック）」を徹底。
* **運用の再生産性（Event Cloning）:** 主催イベント履歴の一元管理と、過去イベントのワンクリック複製により、定期開催イベントの立ち上げコストをゼロ化する。

### 2.3. 成功指標（KPI / ガードレール指標）

| 指標区分 | 指標名 | 目標値 | 計測定義 / 意図 |
| :--- | :--- | :--- | :--- |
| **UX摩擦** | Time-to-RSVP | 15秒以内 | 参加ページ到達から出欠登録完了までの所要時間中央値 |
| **転換性** | 参加後アカウント転換率 | 20%以上 | 未登録で出欠したユーザーが、確認画面等から会員登録を完了した割合 |
| **整合性** | 編集競合発生率 | 0% | 複数幹事による上書き事故（Lost Update）の発生件数 |
| **安全性** | 参加者情報漏洩インシデント | 0件 | 参加者画面から他者一覧APIへの不正アクセス・流出件数 |
| **再利用性** | イベント複製作成率 | 30%以上 | 2回目以降のイベント作成において「過去イベント複製」が選択された割合 |

### 2.4. 認証・データ保持のコスト＆ライフサイクル設計

#### ユーザー状態の二層構造と保持ポリシー
* **匿名参加ステート（Ephemeral User）:**
  * トークン／暗号化Cookie／ローカルストレージで端末に紐付け。
  * 保持期限: イベント終了後30日（TTL満了で自動クリーンアップ、または永続保持せず論理フラグ管理）。
  * 認証基盤（Auth0 / Firebase / Supabase等）のActive User課金を消費させず、RDBMSの軽量レコードとして処理。
* **認証済み会員ステート（Hydrated Member）:**
  * 本会員登録と会員ログインは、Googleアカウントでのサインインを必須とする。出欠だけの匿名参加にはアカウントを求めない。
  * Google から受け取る識別子（`sub`）で会員を一意に結び、表示名とメールアドレスを初期値にする。会員はパスワードを持たない。
  * サインイン完了時に、既存の匿名回答レコードが保有していた UUID をユーザーIDへ昇格・バインドする。
  * パスキー、LINE、マジックリンクは、Googleサインインに加える追加手段である。これらが無くても、Googleサインインがあれば本会員登録の要件は満たす。
* **インフラ原価:** 匿名参加者が数万規模にスケールしても、認証IdPのMAU課金対象外となるため、原価はDBストレージ費用（月額数ドル〜数十ドル程度）のみに抑止可能。

### 2.5. やらないことリスト（Non-Goals）

開発スコープの肥大化と保守複雑性を抑止するため、初期バージョン（MVP）において以下を明確に対象外とする。

1. **リアルタイム文字単位共同編集（CRDT / OT）の実装:**
   * FigmaやGoogle Docsのような同時打鍵同期は行わない。「排他ロックによる単一編集権の付与」に留め、実装・保守複雑度を最小化する。
2. **多階層なロール・権限マトリクス（RBACの過剰設計）:**
   * 「オーナー」「編集者」「閲覧者」「モデレーター」等の複雑な階層は作らず、「幹事（閲覧・編集・一覧閲覧）」と「参加者（回答・自回答照会）」の2値制御とする。
3. **出欠確定時の強制パスワード設定:**
   * パスワード管理の認知的負荷を排除するため、初期登録時のパスワード設定フローは設けない。

## 3. 想定される3つの自己反証と構造的批判

本企画を実装・運用するにあたり想定されるリスク要因と批判的視座である。

### 批判1: ケイパビリティURL紛失と他者なりすまし改ざん（Identity Hijacking vs. Zero-Friction）
* **内容:** 会員登録不要で名前だけで出欠登録できる設計は、「ブラウザのCookieやプライベートブラウズ終了に伴う確認不可」を招く。また、同姓同名の衝突や、第三者が悪意を持って欠席に変更するリスクを排除できない。
* **対抗仮説（Capability Token Pattern）:** 出欠登録時に暗号学的に安全なランダムトークン（NanoID / UUIDv4）を生成し、ローカル保持に加え「確認・変更専用URL」を提示。Cookieが消えてもURLを保持していればアクセス可能とする。また、他者からは編集不可能なCapabilityモデルを採用し、名前の一致ではなくトークンの一致でのみ更新を認可する。

### 批判2: 排他編集ロックの放置によるワークフロー死滅（The Abandoned Lock Risk）
* **内容:** 「同時編集不可」を担保するために画面を開いた幹事が編集権を取得する場合、その幹事がブラウザタブを開いたまま離脱・放置すると、他の幹事が一切編集できなくなる。
* **対抗仮説（Lease-based Lock & Takeover）:** ロックに有効期限（TTL: 例3分）を設け、クライアントからの定期ハートビートで延長する「リースロック」とする。無操作時は自動解放するほか、緊急時に他幹事が「編集権を引き継ぐ（Takeover）」アクションを実行できるフォールバックを組み込む。

### 批判3: 会員化インセンティブの希薄化トラップ（The Frictionless Utility Trap）
* **内容:** 「会員登録しなくても出欠でき、後から確認もできる」状態が快適すぎると、ユーザーが会員登録する動機が失われ、プラットフォームにLTV（顧客生涯価値）の高い会員データが蓄積されない。
* **対抗仮説（Progressive Endowment Effect）:** 「参加イベントが複数溜まる」「過去の回答傾向を再利用したい」「リマインド通知を受け取りたい」という蓄積価値（保有効果）をレバレッジにする。2回目以降の参加時、またはイベント終了後の振り返りタイミングで「1クリックで過去の全参加履歴を保存」と提示することで、自然な転換を促す。

## 4. 難易度順の参照フレームワーク

本企画要件をより堅牢なプロダクト設計へと深化させるための3段階の参照ソースである。

* **Step 1（基礎原理）: Butler Lampson『Protection』(1971) / Capability-Based Security**
  * *視座:* 「ユーザー認証（Identity）に基づきリソースを保護する（ACL）」のではなく、「操作権限を内包したトークン（Capability）を所持している者に権限を与える」という認可の根本原理。
  * *脱ローカルミニマム:* 「未登録ユーザーだから安全な管理ができない」という思い込みを排し、署名付きトークン/ケイパビリティURLによって認証基盤なしで安全な編集・確認境界を構築する。
  * *他分野との接続:* 物理世界の「ホテルのカードキー（誰が持っているかではなく、キーの所持者が解錠できる）」や暗号通貨の署名トランザクション。
* **Step 2（実装・実践）: Martin Fowler『Patterns of Enterprise Application Architecture』(Pessimistic Offline Lock)**
  * *視座:* Webアプリケーションにおける複数ユーザー間の競合防止パターン。悲観的オフライントランザクションとセッションリースの設計。
  * *脱ローカルミニマム:* 「リアルタイム同期（CRDT等）を組む（過剰開発）」か「後勝ち上書きでデータ破壊（手抜き）」かの二者択一を抜け出し、Web標準のステートレスアーキテクチャに適した軽量排他制御を選択する。
  * *他分野との接続:* 航空券・ホテル予約の「座席・部屋の15分間仮押さえ」システム。
* **Step 3（最先端の限界）: Alex Petrov『Database Internals: A Deep Dive into Distributed Systems』**
  * *視座:* 分散環境（複数インスタンス、サーバーレス環境）における排他ロックの一貫性とタイムアウトの境界。
  * *脱ローカルミニマム:* 単一サーバーのメモリ上ロックで済ませてしまい、クラウド環境での水平スケール（Cloud Run / AWS Lambda / 複数Pod）時に同時編集防止が破綻する設計ミスを未然に防ぐ。
  * *他分野との接続:* 分散合意アルゴリズム（Raft/Paxos）におけるリーダー選定ハートビート。

## 5. 次工程（要件定義書）に向けた確認・ヒアリング事項

本企画要件定義書をベースに、次工程である**システム要件定義書・データモデル設計**へ進めるための確認事項である。

1. **未登録ユーザーの「あとから確認」のアクセス経路:**
   * **案A（完全匿名・端末依存）:** 回答完了画面で専用URLを提示＋ブラウザ（Cookie/LocalStorage）に保存。同じ端末・ブラウザからアクセスすれば自動認識。
   * **案B（連絡先紐付け）:** 出欠登録時にメールアドレス（またはLINE連携等）の入力を任意/必須とし、そこに「確認・変更URL（マジックリンク）」を自動送信する。
2. **幹事の「イベント作成時」の会員登録要否:**
   * 幹事についても、参加者と同様に「最初は未登録でイベントページを作成でき、あとから会員登録する」形とするか、あるいは「イベントを作成・主催する幹事は最初から会員登録が必須」とするか。
3. **複数幹事の追加・招待方式:**
   * 共同幹事を追加する際、「幹事用URLを共有すれば誰でも幹事になれる（URL共有型）」か、あるいは「既存幹事がメールアドレスやIDで特定ユーザーを招待・承認する（招待制）」とするか。
4. **「同時編集不可」の制御 UX:**
   * 他の幹事が編集中である場合、
     * **挙動A（閲覧のみ・編集不可）:** 編集画面に入ろうとすると「現在〇〇さんが編集中です（残り2分）」と表示され、編集フォームが非活性（Read-Only）になる。
     * **挙動B（強制引き継ぎ可）:** 放置されている可能性を考慮し、「編集権を引き継ぐ（前の人の編集は破棄）」ボタンを設ける。
